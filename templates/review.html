THE PROBLEM

Reports lose visibility

Email and scattered messages can make it hard to see who owns a repair or whether it has been completed.

OUR APPROACH

One traceable request

Students report issues. Administrators assign work. Maintenance workers record progress and the final fix.

WHY THIS SCOPE

Clear responsibility

A focused campus workflow with role-specific access and visible change history. The team can demonstrate the full path in a classroom prototype.

INITIAL ARCHITECTURE

Simple enough to build and explain

Django · SQLite · Local CSS

We chose a single Django application to keep authentication, forms, and workflow checks together. SQLite keeps the classroom setup small; production scale would require a separate deployment review.

MIDPOINT REVIEW

Help us shape the next iteration

We have kept the first build focused on a complete request-to-resolution path. The main risk is inconsistent access or status behavior, so workflow rules live on the server and are covered by direct tests.

  • Should resolved requests stay closed, or should a later version support reopening?
  • Should requesters be able to edit a report before a worker is assigned?
  • What usability or quality check should the team prioritize next?
